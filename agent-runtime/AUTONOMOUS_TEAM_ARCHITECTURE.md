# FreeDom — архитектура автономной команды Eve

Статус: целевая архитектура режима High Autonomy. Реализуется поэтапно в feature-ветках. Production и `main` защищены.

## Цель
Владелец отправляет одно большое ТЗ. Orchestrator планирует работу, вызывает специалистов, организует реализацию, независимое тестирование, цикл исправлений и отчёт. Владелец подключается только к фактическим неизвестным, необратимым действиям, финансовым решениям, изменениям безопасности и Production.

## Состав команды
1. **Orchestrator (root)** — анализирует ТЗ, читает контекст, делегирует, строит граф задач, разрешает конфликты, контролирует критерии приёмки и отчёт.
2. **Designer** — визуальная система, UX/UI, адаптивность, фото-слоты.
3. **Programmer** — единственный агент, который изменяет прикладной код, создаёт коммиты и Pull Request в назначенной feature-ветке.
4. **Motion** — карта анимаций, переходов, жестов и reduced-motion.
5. **Tester** — независимые тест-кейсы, регрессия и классификация PASS/FAIL/NOT TESTED.
6. **Mentor** — анализирует доказательства завершённых задач и предлагает улучшения инструкций, skills, knowledge и evals. Не редактирует их сам и не меняет код.

## Права и изоляция Eve
Eve declared subagents не наследуют authored tools/extensions/skills/connections/sandbox root-агента. Поэтому каждый специалист получает только собственные capabilities.
- Root монтирует GitHub preset `repo-explorer` (read-only).
- Designer, Motion и Tester монтируют `repo-explorer` для чтения текущего кода и независимого аудита.
- Programmer монтирует GitHub preset `maintainer` через существующий Vercel Connect connector. Записи остаются за встроенными approval gates.
- Mentor не получает GitHub write-инструменты.
- Не добавлять инструменты, способные затронуть Production, секреты, платежи или Supabase grants/RLS без отдельного проектирования и согласования.

## Pipeline одной большой задачи
1. **Intake:** Orchestrator извлекает цель, scope, ограничения, критерии приёмки и неизвестные факты.
2. **Impact analysis:** Designer, Motion, Programmer и Tester независимо исследуют свою область. Каждому передаётся полный контекст, так как child session не наследует историю родителя.
3. **Plan:** Orchestrator объединяет результаты, фиксирует зависимости, назначает владельца каждого файла и определяет последовательность. Один файл — один исполнитель.
4. **Implementation:** Programmer работает только в task branch, делает маленькие коммиты и сохраняет обратимость изменений.
5. **QA:** Tester проверяет изменённые и соседние сценарии, отдельно помечая статические, автоматические и браузерные проверки.
6. **Repair loop:** FAIL возвращается Programmer с шагами воспроизведения и ожидаемым поведением. Повторять проверку до PASS или исчерпания лимита попыток.
7. **Learning review:** Mentor получает ТЗ, итоговые коммиты, отчёты, дефекты и обратную связь владельца. Возвращает только предложения с доказательствами, причиной, областью применения и уровнем уверенности.
8. **Knowledge approval:** Orchestrator проверяет предложения Mentor на повторяемость, конфликт с решениями владельца и побочные эффекты. Только затем создаёт отдельное изменение knowledge/skills/evals, которое проходит ревью.
9. **Delivery:** Orchestrator предоставляет PR, Preview URL, список изменений, реальные результаты тестов, известные ограничения и необходимые решения владельца.

## Правила обучения
Mentor не переобучает веса модели. Он формирует организационную память:
- `knowledge/project-context.md` — проверенные сведения о проекте и ссылки на источники;
- `knowledge/design-decisions.md` — утверждённые визуальные и UX-решения;
- `knowledge/technical-architecture.md` — подтверждённая техническая архитектура;
- `knowledge/known-bugs.md` — воспроизводимые дефекты и статус;
- `knowledge/lessons-learned.md` — повторяемые уроки и ссылки на PR/тесты;
- skills — пошаговые процедуры для повторяющихся задач;
- evals — контрольные сценарии для измерения качества агентов.

Не записывать гипотезы как факты. Каждое новое правило должно иметь источник, дату/коммит, область действия и критерий проверки. Устаревшие правила не удалять без проверки: помечать superseded и ссылаться на замену.

## Контрольные точки и согласования
**Автономно:** чтение репозитория, анализ, планирование, исправления обратимых багов в feature branch, тесты, Preview deployment, повторные исправления в рамках ТЗ.

**Требуется согласование владельца:** Production deploy/alias promotion, merge в main, удаление файлов/данных, изменения Supabase schema/RLS/grants/roles, реальные бронирования и платежи, авторские факты/история, новые платные сервисы и увеличение лимитов, отключение SSO/защиты, необратимые операции.

## Модель и провайдер
Текущий выбранный провайдер — Yandex AI Studio. Все шесть агентов используют общий адаптер `agent/provider.ts` на базе `@ai-sdk/openai` (версия 4.x, согласованная с AI SDK 7 из Eve 1.0.0-rc.6) и OpenAI-совместимого Chat Completions API.
- Base URL: `https://ai.api.cloud.yandex.net/v1`.
- Модель передаётся как полный URI `gpt://<folder-id>/<model>` через `YANDEX_MODEL_URI`.
- Folder ID передаётся через `OpenAI-Project`; API key — через `Authorization: Api-Key ...`.
- Используется Chat Completions (`provider.chat()`), поскольку Yandex документирует function calling для этого endpoint.
- Секреты хранятся только в Vercel server-side Environment Variables: `YANDEX_API_KEY`, `YANDEX_FOLDER_ID`, `YANDEX_MODEL_URI`.

Совместимость на уровне API подтверждена документацией провайдера и Yandex. Рабочий модельный вызов, streaming и function calling должны быть проверены на Preview после установки пользовательских credentials. До этого runtime не считается функционально готовым.

## Definition of Done
- Все критерии приёмки выполнены или явно перечислены блокеры.
- Все изменённые файлы принадлежат назначенным исполнителям.
- Tester дал фактический PASS/FAIL/NOT TESTED.
- Исправления прошли повторную проверку.
- Mentor сформировал learning review, но его предложения не применены без проверки.
- Preview и commit/PR подтверждены.
- Production не изменён.
- Владелец получает ясный отчёт без неподтверждённых заявлений.
