## Краткий вывод

Проект уже имеет широкую функциональную основу: публичные страницы, отдельные CRM-разделы, API-прокси и три активные Supabase Edge Functions. Главный риск сейчас — не нехватка новых экранов, а необходимость подтвердить безопасность финансовых RPC и провести реальное регрессионное тестирование ключевых сценариев.

Старый `AUDIT_REPORT_2026-11-10.md` содержит серьёзные замечания по SECURITY DEFINER RPC. Они остаются важными сигналами, но не должны автоматически считаться подтверждённым текущим состоянием: текущая read-only проверка схемы Supabase не прошла из-за ошибки аутентификации read-only пользователя, а Security Advisor сообщил, что проект находится в hibernated состоянии. Поэтому SQL-изменения сейчас не выполнялись.

### Backend / интеграции
На подключённом Supabase project `vutmbhsclmcfqqlzxqkc` перечислены три активные Edge Functions:
- `create-public-booking` — ACTIVE, `verify_jwt=false`; использует service-role только внутри серверной функции и вызывает RPC `create_public_booking`.

### Найденная и исправленная проблема клиентского кода
В `profile.html` ошибки Supabase и исключения вставлялись в DOM через `innerHTML`. Сообщения ошибок являются динамическими данными, поэтому такой способ создаёт ненужную HTML injection поверхность.

Исправлено в отдельном коммите:
- добавлен `showLoadingError()`;
- сообщения теперь вставляются через `textContent`;
- все три динамических вывода ошибок через `loadingState.innerHTML` удалены.

### Дополнительный риск регистрации, требующий backend-проверки
Регистрация Supabase Auth и создание строки профиля в `users` выполняются отдельными запросами из браузера.
