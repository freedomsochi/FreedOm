# FreeDom — журнал улучшений процесса

## Правила
Каждое изменение метода работы должно быть оформлено как эксперимент: проблема → baseline → изменение → ожидаемый эффект → измерение → решение. Не внедрять несколько несвязанных изменений одновременно.

## Эксперименты

### PI-001 — Design Specification до начала coding
- Статус: PROPOSED.
- Проблема: неоднозначная передача визуальных требований повышает риск переделок.
- Изменение: обязательная спецификация для существенных UI-задач по `DESIGN_SPEC_TEMPLATE.md`.
- Baseline: cycle time и rework rate пока NOT MEASURED.
- Ожидаемый эффект: меньше уточнений после начала coding и меньше повторной реализации.
- Метрика: SPEC_COMPLETENESS, SPEC_AMBIGUITY, FIRST_PASS_RATE, REWORK_RATE.
- Проверка: после двух сопоставимых циклов.
- Решение: пока не оценено; правило пилотируется на новых задачах, не требует массового переписывания старых ТЗ.

### PI-002 — Визуальные доказательства как обязательный вход и выход
- Статус: PROPOSED / BLOCKED BY BROWSER ACCESS.
- Проблема: CSS/HTML review не подтверждает визуальный результат.
- Изменение: before/after screenshots с viewport, Preview URL и exact SHA.
- Baseline: скриншоты текущего SHA не представлены в доступных отчётах.
- Ожидаемый эффект: раньше выявлять перекрытия, clipping, композиционные и адаптивные дефекты.
- Метрика: VISUAL_REFERENCE_COVERAGE и доля задач с browser evidence.
- Проверка: после восстановления доступного браузера/Preview.
- Решение: не объявлять визуальный аудит выполненным до появления доказательств.

## Следующий эксперимент
PI-003 — task start/finish timestamps и единый acceptance checklist для расчёта cycle time и FIRST_PASS_RATE. До накопления двух циклов KPI скорости не рассчитывать.
