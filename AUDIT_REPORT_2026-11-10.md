## Критические и высокоприоритетные замечания

### P0 — авторизация финансовой операции отсутствует в SECURITY DEFINER RPC

Функция `public.record_event_registration_payment(p_registration_id, p_amount, p_payment_method)`:
- имеет `SECURITY DEFINER`;
- доступна роли `authenticated`;
- не проверяет `auth.uid()`, email, роль администратора или иное право доступа;
- создаёт запись в `payments`, создаёт `payment_allocations` и изменяет `event_registrations.paid_amount/payment_status`.

Следствие: любой вошедший пользователь, который сможет получить ID регистрации, потенциально может записать оплату от имени гостя. Это не просто advisor warning — это подтверждённая по определению функции проблема контроля доступа.

Рекомендация: закрыть EXECUTE для обычных пользователей и разрешить только подтверждённому администратору; добавить явную null-safe серверную проверку полномочий. Перед миграцией проверить все реальные вызовы и роль этой функции в CRM. Изменение не применялось.

### P1 — потенциальный обход email-проверки через NULL

У ряда SECURITY DEFINER функций встречается проверка вида `IF auth.email() <> '<admin>' THEN ...`. В PL/pgSQL сравнение с NULL возвращает NULL, а ветка IF при NULL не срабатывает. При наличии authenticated-сессии без email claim такая проверка может не запретить операцию.

Подтверждённые функции с таким шаблоном включают:
- `admin_get_bookings`;
- `admin_get_kitchen_orders`;
- `cancel_booking`;
- `confirm_booking`;
- `create_manual_guest`;
- `add_service_order`.

Рекомендация: заменить такие проверки на null-safe `auth.email() IS DISTINCT FROM '<admin>'` и одновременно требовать `auth.uid() IS NOT NULL` там, где это необходимо. Проверить остальные SECURITY DEFINER функции тем же способом. Не делать массовый revoke без анализа намеренно публичных RPC.

### P1 — публичные endpoints без защиты от автоматизированного спама

- Edge Function `create-public-booking` работает с `verify_jwt=false`, использует service-role key на сервере и вызывает ограниченную SQL-функцию `create_public_booking`. Секрет остаётся на сервере, что правильно; RPC валидирует даты, гостя, вместимость и конфликт подтверждённых броней.
- Edge Function `public-availability` также имеет `verify_jwt=false`, принимает публичный POST и использует anon key. Это ожидаемо для публичной проверки доступности.
- В просмотренных реализациях не обнаружены rate limiting, CAPTCHA или другой устойчивый антибот-контроль. CORS разрешает `*`.

Риск: массовые фиктивные заявки на бронирование/события могут засорять CRM и увеличивать нагрузку. Рекомендация: добавить rate limiting по IP/телефону, honeypot/CAPTCHA по порогу риска, лимиты длины/частоты и мониторинг всплесков. Не закрывать публичные сценарии JWT-обязательностью без изменения пользовательского потока.

### P1 — парольная защита Supabase Auth

Supabase Security Advisor сообщает, что защита от скомпрометированных паролей (проверка HaveIBeenPwned) отключена. Включить её в настройках Auth после проверки текущей политики паролей и пользовательского UX.

## Средний приоритет

### P2 — публичные и административные RPC требуют единой матрицы доступа

Security Advisor показывает:
- 7 публично исполняемых SECURITY DEFINER функций;
- 32 SECURITY DEFINER функции, исполняемые authenticated;
- 1 предупреждение о выключенной защите скомпрометированных паролей.

Часть публичных RPC выглядит намеренной: `create_public_booking`, `create_event_registration`, `get_home_events`, `get_public_availability`, `get_public_room_availability`, `get_public_rooms`. Их не следует автоматически закрывать. Отдельно проверить `confirm_public_booking`: она доступна anon на уровне grants, но сама требует email администратора и должна быть закрыта от anon на уровне EXECUTE.

У большинства новых административных RPC обнаружена явная проверка admin email. Однако единая роль/таблица администраторов надёжнее, чем повторяющийся hard-coded email в SQL-политиках и функциях.

### P2 — две реализации публичной доступности комнат расходятся

В базе присутствуют:
- `get_public_availability` — считает брони со статусом `новое/new` занятыми;
- `get_public_room_availability` — считает только подтверждённые/активные статусы;
- `create_public_booking` — при проверке конфликта также учитывает только подтверждённые/активные брони.

Текущая Edge Function `public-availability` вызывает `get_public_room_availability`, то есть основной edge-путь ближе к логике создания брони. Старые страницы или клиенты, вызывающие `get_public_availability`, могут показывать другое состояние. Нужна карта всех клиентов и единый контракт доступности. У `get_public_room_availability` также нет верхней границы периода, в отличие от `get_public_availability`.

### P2 — CRM опирается на RPC как на серверный барьер, но не все страницы имеют явный session gate

Некоторые страницы CRM загружают оболочку без предварительного `auth.getSession()` и сразу вызывают административные RPC. Это не заменяет проверку безопасности в БД: RPC должны самостоятельно отклонять не-администраторов. Но пользовательский UX лучше сделать единым: проверка сессии, понятный редирект на вход, обработка истёкшей сессии и отсутствие ложного состояния «загрузка».

Особое внимание — всем RPC, меняющим деньги, статусы бронирования, заказы и регистрации. Проверка должна быть внутри БД, не только в JS.

### P2 — профиль показывает ссылку на старую админ-панель

В `profile.html` ссылка «Админ-панель» ведёт на `admin.html`, тогда как актуальная CRM-навигация ведёт через `admin_v10_dashboard.html`. Сама видимость ссылки не является контролем доступа, но маршрут и отображение нужно привести к единой модели ролей.

### P2 — бронирование через Formspree не является подтверждённой бронью

`room-booking-form.html` отправляет форму в Formspree и корректно сообщает, что заявка не подтверждает размещение. Даты и выбранный вариант передаются клиентом; скрытое поле доступности также может быть изменено пользователем. Нельзя использовать это значение как серверное подтверждение наличия мест. Нужна серверная перепроверка доступности перед подтверждением заявки. Honeypot есть, полноценного rate limit в клиентском коде нет.

## Производительность и качество базы

Supabase Performance Advisor сообщает:
- 6 случаев нескольких permissive RLS policies для одной роли/операции (в частности events, payments, service_orders, veg_raw_menu);
- 5 групп дублирующихся индексов (bookings, orders, payments);
- ряд неиспользуемых индексов на payments, veg_raw_menu, event_registrations, space_locations, orders, services и других таблицах.

Не удалять индексы автоматически: часть может быть недавно создана, нужна для будущей нагрузки или не иметь статистики использования. Сначала проверить планы запросов, нагрузку и статистику за репрезентативный период. Пересмотреть дубли политик так, чтобы не менять доступ.

Положительный результат: у просмотренных таблиц схемы public RLS включён; у SECURITY DEFINER функций задан фиксированный search_path. Это хорошая база, но не заменяет проверки внутри каждой функции.

## Интерфейс и архитектура сайта

### Пользовательские страницы
- Главная `index.html` — около 120 KB, большой монолитный файл с CSS и JS, орбитальной навигацией, переходами и медиа. Важно сохранить текущую механику и визуальное направление; изменения лучше делать небольшими и проверять на телефоне.
- `rooms-eco-futurism-v2.html` — около 90 KB; это действующая утверждённая страница комнат. Не подменять её экспериментальными `rooms-architectural-v1/v2`.
- `freedom-events-v1.html`, `freedom-banya-v2.html`, `kitchen-pixel-v2.html`, `space.html` — также крупные автономные HTML-файлы. При дальнейшем развитии полезно выделять повторяющиеся компоненты/стили, но только после регрессионного покрытия.
- Сайт содержит много исторических/экспериментальных HTML-файлов в корне (109 файлов корневого уровня в текущем дереве). Нельзя удалять их массово: сначала составить карту входящих ссылок, Vercel routes и CRM-зависимостей.

### Доступность и адаптивность
В проверенных страницах есть отдельные responsive-стили; в events/rooms/space обнаружены aria-label и/или reduced-motion правила. Наличие CSS-правил ещё не доказывает корректную работу на устройстве. Нужна ручная проверка:
- Android Chrome/Yandex Browser: портрет/альбом, 360–430 px, свайпы, drag, клавиатура не применима на touch;
- Desktop: 1280–1440 px, мышь, клавиатура, focus-visible;
- reduced motion, контраст текста на фото, масштабирование шрифта, safe-area;
- загрузка фото и переходы между страницами без вспышек старого фона/скачков layout.

### Формы и данные
- Проверить все формы на валидацию, повторную отправку, двойной submit, сообщения об ошибках, корректную обработку сети и доступность полей.
- Проверить, что клиентские hidden/query-параметры никогда не являются источником истины для цены, роли, статуса или доступности.
- Все данные из БД, отображаемые через `innerHTML`, должны проходить экранирование. Использовать `textContent` там, где HTML не нужен.
